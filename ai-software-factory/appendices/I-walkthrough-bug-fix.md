# Appendix I – End-to-end walkthrough: bug fix

Illustrative. This walkthrough is the end-to-end flow that the Minimum Viable Harness must demonstrate first (§15.0): one repository → Bug Fix workflow (Appendix C) → review checkpoints and approval → independent verification → evidence → knowledge reconciliation. The pilot represents states and sub-states with issue/PR labels and CI check runs.

| # | Step | Actor | Artifact / state |
|---|---|---|---|
| 1 | A developer starts a task from issue CICD-4821; policy selects workflow `bug-fix@1.0.0` (`ACTIVE`) | Requester | `TRIAGED` (label on the issue) |
| 2 | Intake completes the Task brief fields: outcome "a timed-out job is retried exactly once more"; AC-1..AC-3; revert = revert commit, no data changes. The requester confirms | Intake agent + requester | Change Brief; `CheckpointRecord` `requirement-review` = passed |
| 3 | Classification: paths under `src/domains/pipeline/retry/**`, not protected; business logic → Medium; reversibility High → A2 (1 independent human approval). `plan-review` is recorded by policy as `not-applicable` (not High, reversibility not LOW) | Policy | `PolicyDecision` |
| 4 | Context is resolved progressively: `AGENTS.md` → module boundaries (pipeline) → `REVIEW.md` (pipeline) → `SPEC-PIPE-RETRY@3` → contract `pipeline-api-v2@2.3.0` → existing retry tests. The basis is recorded; every artifact is `ACTIVE` | Investigator | `CONTEXT_READY` / `REPRODUCING`; `basis` |
| 5 | The verifier writes a failing reproduction test from AC-1 in a separate context; the test fails on the base SHA | Verifier | `CONTEXT_READY` / `REPRODUCED`; reproduction evidence; test is read-only for the implementer |
| 6 | Diagnosis: the code retries up to 3 times, while the spec says exactly once. The agent records knowledge conflict `KC-2026-0045` and proposes treating it as an implementation defect; the product owner confirms. The spec is not edited (§4.7) | Investigator + product owner | `PLANNED` / `ROOT_CAUSE_IDENTIFIED`; `KnowledgeConflict` resolved |
| 7 | Handoff verifier → implementer with the reproduction test and evidence; the implementer checks the required artifacts and accepts. A draft PR is opened; implementation happens in a worktree pinned to the base SHA | Implementer | `EXECUTING` / `FIXING` (state now lives on the PR labels); `Handoff` accepted |
| 8 | Handoff implementer → verifier in `VERIFYING`, pinning the head SHA and excluding the implementer's notes. Profile `backend-service-v1` runs via verification adapters; the retry tests run in stress mode (the path is tagged timing-sensitive). Integrity sensor: 1 `integrity.expected-value-edit` hit on the old test asserting 3 retries; the assertion belongs to a test linked to AC-2, so the hit is shown at `warn` level with the old/new value pair for the approver (§7.13). An untouched test that is in the flaky registry hits `ERROR` because the runner lost its connection, is retried once per §6.14, and passes | Verifier | `VERIFYING` → pass; `CheckpointRecord` `independent-verification` = passed |
| 9 | Pre-PR review with a fresh context; AI review: hunters raise 4 candidates; the verifier confirms 1 Important and 1 Pre-existing; one Nit is dropped. The agent fixes the Important finding → `VERIFYING` → re-review on the clean diff only (round 2 of 3) | Review pipeline | `REVIEWING`; findings dispositioned |
| 10 | Knowledge impact: the change touches `src/domains/pipeline/retry/**`. The agent proposes: `DOC-PIPELINE-RETRY-ARCH` (`implementation-description`) describes "retries up to 3 times" → `update` in the same PR; `SPEC-PIPE-RETRY@3` (`intent`) → `keep`, because the implementation now matches the spec and the product owner confirmed in step 6. Both decisions are `proposed` until step 11 | Improvement agent | Reconciliation proposal in the PR |
| 11 | The PR is opened with the Appendix G template. The requester signs off; an independent code owner reads the Risk section, "what the checks would not catch", Knowledge impact and the operational readiness record, then approves SHA `def5678` (tier Medium, §9.10). As the code owner of the area, this person also confirms both reconciliation decisions (§5.10) and the tier Medium `release-readiness` (§6.12); no additional person is needed | Human | `AWAITING_MERGE_APPROVAL` → approved; checkpoints inferred from PR review events |
| 12 | The merge queue reruns the required checks on the latest main | CI | `IN_MERGE_QUEUE` → `MERGED` |
| 13 | Staged release with the signals confirmed in step 11 (retry error rate, duplicate execution count); the Change Shepherd monitors during the observation window. After merge, the trusted mechanism updates `validatedAgainst` of both artifacts with the commit on main (§5.10) | Change Shepherd | `RELEASING` → `OBSERVING` → `COMPLETED` |
| 14 | Learning: the Pre-existing finding becomes a gardening issue; workflow metrics are recorded: lead time by sub-state, **3 human touches** (requester, product owner because of the knowledge conflict, code owner; 2 without the conflict), 1 independent approval, 2 review rounds, 1 retry due to `ERROR`, 0 rejected handoffs, approval wait time, CI minutes, model cost versus the task cost ceiling | Feedback plane | Workflow metrics (§13.7) and gardening issue |

**Variant: basis changes mid-task.** If at step 7 the product owner supersedes `SPEC-PIPE-RETRY@3` with a new spec that allows retries with backoff, the task runner flags that the basis has changed; the task continues independent work but cannot pass the merge approval gate. The product owner decides `reapprove`: acceptance criterion AC-2 is amended through `requirement-review`, the earlier approval is invalidated, and the task returns to `PLANNED` (§6.5).
