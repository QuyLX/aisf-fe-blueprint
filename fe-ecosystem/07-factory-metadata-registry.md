# 7. Factory: metadata, registries, repository standard

<a id="s7-1"></a>

## 7.1. Canonical IDs

| Type | Convention | Example |
|---|---|---|
| Archetype | kebab-case enum | `operational` |
| Capability pack | `cap:<id>` | `cap:attachments` |
| Profile | `<scope>:<id>` | `baseline`, `archetype:public-web`, `x:a11y` |
| Check | `<domain>.<name>` | `seo.canonical` |
| Rule | `FE-<AREA>-<NNN>` | `FE-API-001` |
| Surface | `<app>/<surface>` | `console/iam` |
| Task class | `<scope>.<kind>` | `docs.link-fix`, `codemod.apply` |
| Playbook (workflow spec) | ID of the `coreWorkflow` or the profile's own ID, with `@<semver>` | `bug-fix@1.0.0`, `console-module@1.2.0` |

Every reference must point to an ID that exists in the registry; registry CI and `factory doctor` enforce this.

**Registries and indexes are files in Git and CI, not a catalog service** ([§0.4](00-summary.md#s0-4)). Registries (IDs, Check Registry, trust registry, path-risk map, Journey Registry) are schema-backed files in the policy repo, the platform repo or a product repo, changed via PR. The portfolio index, Token Usage Index, Test Asset Catalog and Knowledge Index are artifacts regenerated by CI and published with provenance. The Factory does not run its own catalog service; before building the Knowledge Index or the Test Asset Catalog, an existing developer portal or catalog is evaluated as the place to host or display them ([§17](17-decisions-to-make.md#s17)).

**Task classes** are defined explicitly in the registry per Standard §9.4: one `ACTIVE` playbook (`id` and major), one scope (repo, surface or group of surfaces) and one ceiling sub-tier. For example, `docs.link-fix` = `docs-update@1`, scope repo `docs`, ceiling R0. Trust earned in one class does not transfer to another class, even with the same playbook but a different scope or a higher ceiling.

**Vocabulary.** Status, disposition, risk tier, trust level, autonomy level, gate, task state, knowledge artifact state and authority all belong to the Standard (`aisf-vocabulary.yaml`); this profile redefines none of them. The profile only adds via registered extensions ([§18.3](18-aisf-conformance.md#s18-3)): the `release` channel, Knowledge Record `kind`s, sub-states of its own playbooks and rule categories outside Standard §8.1. Every check declares the rules it enforces (`implementsRules`).

## 7.2. Repository descriptor

Every product repo has a `factory.yaml` at its root. It is a **control file** ([§8.7](08-verification.md#s8-7)), so every change to it is classified by dimension ([§10.1](10-autonomy-policy.md#s10-1)).

```yaml
apiVersion: factory/v4
standard: aisf@4.0.0
profile: aisf-frontend@1.1.0
application: console
owner: team-console                  # vertical owner of the repo
backupOwners: [team-console-leads]   # Standard §9.10: ≥ 2 eligible owners or a named backup
lifecycle: active
platform: { channel: stable }        # version window for @platform/* (§4.8)
surfaces:
  - id: console/compute
    owner: team-compute              # module owner, must match CODEOWNERS
    backupOwner: team-console
    paths: ["src/modules/compute/**"]
    routes: ["/compute/**"]
    rendering: authenticated         # authenticated | public-static | docs (§3.2)
    archetypes: [operational]
    capabilities: [cap:workflow-state, cap:bulk-actions, cap:search-filter]
    profiles: [x:a11y, x:perf-app, x:i18n]
    criticality: high                # critical | high | normal — same enum as journeys (§7.7)
    review: { aiMode: shadow, depth: standard }             # Standard §7.9; promotion per §9.9
    autonomy: { zeroHuman: false }                          # A0 opt-in (Standard §9.6)
    slo: { availability: "99.95%", errorBudgetPolicy: default }   # §19.4
contracts:
  consumes: [openapi:compute@1.4, openapi:iam@2.1]
promptAssets: []                     # declared prompt files, exempt from the injection pre-scan (§9.9)
```

`factory doctor --owners` reports every surface or control file with fewer than two eligible owners.

**Discovery by convention:** the **portfolio index** is *generated* (periodically and on merge) from the descriptors, lockfiles, routes, OpenAPI, Storybook index and import/token scans of every repo — there is no hand-written catalog. `factory doctor` reports drift between declared and discovered information: paths that belong to no surface, contracts used without being declared, surface owners that do not match CODEOWNERS, critical journeys missing tests.

## 7.3. Knowledge Records and the source of truth for documentation

**Knowledge Record** is the name this profile uses for the Standard's knowledge artifact (Standard §5.8): ADRs, specs, contract specs, policies, threat models, runbooks, component documentation, `AGENTS.md`, `REVIEW.md`, skills and playbooks. Records live in Git with frontmatter containing the Standard's required fields (`id`, `kind`, `status`, `version`, `owner`, `authority`, `describes`, `basedOn`, `supersedes`/`supersededBy` when present, `validatedAgainst`) plus two profile fields (`x-fe.appliesTo`, `x-fe.visibility`). `factory context <path>` / `--diff` returns the governing records. Records are written in the present tense; history lives in the decision log; audit results live in evidence.

- `status` uses the Standard's lifecycle unchanged: `DRAFT`, `PROPOSED`, `ACTIVE`, `NEEDS_REVALIDATION`, `SUPERSEDED`, `DEPRECATED`, `ARCHIVED`. **Only `ACTIVE` records are the default basis.** `NEEDS_REVALIDATION` may only be used under the conditions of Standard §5.8 and is not a basis for new tasks at R2 or above until revalidated. Validity is never inferred from modification time or document age.
- **Who changes state.** Transitions to `ACTIVE`, `SUPERSEDED` or `DEPRECATED` are decisions of the corresponding authority via a review checkpoint ([§9.11](09-agent-operating-model.md#s9-11)). Agents, bots and gardening may only transition `ACTIVE → NEEDS_REVALIDATION` (flagging suspicion) and propose other transitions.
- `authority` uses the Standard's enum. The mapping from `kind` to `authority` is in [§18.2](18-aisf-conformance.md#s18-2); the profile's own `kind`s (`component`, `threat-model`, `policy`) are registered as extensions ([§18.3](18-aisf-conformance.md#s18-3)).
- `x-fe.appliesTo` states where the record applies: repo, surface, package with a version range (e.g., `"@platform/server": ">=3 <4"`), contract with version. `factory context` only returns records that match the versions the repo pins.
- `x-fe.visibility`: `public` | `internal` | `restricted`. Determines who may read the record via the Knowledge Index ([§7.8](#s7-8)).

**Knowledge impact analysis (Standard §5.9).** Every PR (channel `code`) runs the `knowledge.impact` check. The check queries the `describes`, `basedOn`, `generatedFrom`, `verifiedBy`, `implements` and `supersedes` relations in the Knowledge Index ([§7.8](#s7-8)), lists affected records in the evidence and the PR description, and:

- `FAIL`s when an affected `ACTIVE` record with authority `intent`, `decision`, `procedure` or `guidance` has no reconciliation decision recorded by the task;
- only `warn`s for `implementation-description` records, which are handled by scheduled reconciliation when not updated in the same PR.

`describes` is declared as narrowly as possible (module, contract, path group); the root `AGENTS.md` declares what it actually describes (standard commands, directory map), not `**`. Discovered relations (links, `@ac` tags, contract references) never override declared relations; differences are reported by `factory doctor` as drift.

**Reconciliation (Standard §5.10).** When a change touches a `describes` scope, a contract changes version, an ADR changes state, a requirement changes, drift is detected, an incident shows documentation is wrong, or an owner is gone, the Factory runs the Standard's six-step process and records a `ReconciliationRecord` with one decision: `keep`, `update`, `supersede`, `deprecate` or `review`. Decision rights follow authority: `implementation-description` is approved by the document owner like code; `intent` (specs, AC in `journeys.yaml`) by the product owner via `specification-review`; `decision` (ADRs) by an architect or code owner via `design-review`; `procedure` and `guidance` per the control file rules. Scheduled reconciliation runs as its own task class (`knowledge-reconciliation`), not bundled with behavior changes.

**When the implementation diverges from the spec (Standard §4.7).** A difference between code and an `intent` or `decision` record is a **knowledge conflict**, not drift. The agent records the conflict and escalates ([§9.4](09-agent-operating-model.md#s9-4)); the agent never edits a spec, AC, scenario, oracle or contract to match the code ([§9.10](09-agent-operating-model.md#s9-10)), and `intent`/`decision` records are never edited automatically.

**Each type of documentation has one source of truth.** Not every type of documentation should go through the CMS. Criterion: documentation that must change together with code or contracts lives in Git and goes through PR; documentation with an editorial lifecycle (scheduling, preview, non-engineer authors) lives in the CMS and goes through verify-on-publish ([§11.4](11-delivery-change-management.md#s11-4)).

| Documentation type | Source of truth | Owner | Publishing channel (view only) | Readers |
|---|---|---|---|---|
| ADR, policy, threat model, contract spec | Knowledge Record in the repo where the decision is in effect (portfolio-level decisions: platform repo or policy repo) | Owner recorded in the record | `factory context`, Knowledge Index | Engineers, agents |
| Runbook | Knowledge Record `kind: runbook` in the app's repo | Vertical owner | Knowledge Index; linked from alerts | On-call, agents |
| API contract and API reference | OpenAPI/AsyncAPI in the service repo, published to the contract registry | Backend service team | Docs Portal (reference), generated clients | Developers, customers, agents |
| SDK reference | Doc comments in the SDK source | SDK owner | Docs Portal | Developers |
| Component documentation | Platform repo ([§5.6](05-design-system.md#s5-6)) | DS maintainer | DS site, Storybook, manifest/MCP | Engineers, agents |
| Product guides (tutorial, how-to, explanation) | Docs-as-code (MDX) in the `docs` repo or the service repo's `docs/` | Product/service team; reviewed by a technical writer | Docs Portal | Customers, developers |
| Repo and module operations documentation | `AGENTS.md`, `REVIEW.md`, `README` in the repo | Code owner | In the repo; Knowledge Index | Engineers, agents |
| Editorial content (announcements, articles, campaign pages) | CMS, per the content model ([§6.4](06-product-patterns.md#s6-4)) | Content owner | Website, announcements on the Docs Portal | Public |
| Changelog, release notes | Generated from work items and the contract registry; editorial additions at the source | Vertical release owner | Docs Portal, Console | Customers |
| Product requirements | Issue tracker (outside Git) | Product owner | Only referenced by ID ([§7.7](#s7-7)) | Product team |

Publishing channels and indexes are always **copies with provenance** (source, commit or revision); when they conflict with the source, the source wins and the copy is rebuilt. Documentation that is not a record (guides, READMEs) uses the same `status` field with the same lifecycle, so agents can distinguish content in effect from drafts, content needing revalidation, or archived content.

## 7.4. AGENTS.md and REVIEW.md

Every repo has a root AGENTS.md of ≤ ~150 lines: what the product is, the directory map, standard commands, hard rules, where to find docs. The platform's standard section is written by the generator between markers and kept in sync by `factory doctor`. Every module has a nested AGENTS.md. Runtime-specific agent files only point to AGENTS.md. Skills and playbooks have a single source; adapters generate the format for each runtime.

**Kept in sync with actual versions and architecture.** Documentation for agents is only useful when it is correct for the repo being worked on:

- **A generated "Platform facts" block**, between markers in AGENTS.md: Next.js, React and `@platform/*` versions taken from the lockfile; contracts in use with versions taken from `factory.yaml`; surfaces and rendering profiles; pinned skill and playbook versions. `meta.agents-md-drift` fails when this block drifts from the lockfile or the descriptor.
- **Hand-written sections are reference-checked:** `factory doctor` reports paths, commands, packages or record IDs that are mentioned but no longer exist.
- **Skills and playbooks declare `appliesTo`** (version range of `@platform/*`, profile, rendering profile). The Factory only loads skills compatible with the versions the repo pins; an incompatible skill is not loaded and is a `factory doctor` finding.
- **Version upgrades carry documentation along:** `factory upgrade` ([§9.6](09-agent-operating-model.md#s9-6)) regenerates the Platform facts block and bumps skill pins in the same PR as the package upgrade, so code and agent guidance never diverge across a merge.
- **Distinguishing states:** `factory context` returns every document with its `status`, `authority`, version and source ([§7.3](#s7-3)). Agents treat only `ACTIVE` as the default basis; `NEEDS_REVALIDATION` under the conditions of Standard §5.8; other states may only be used as reference when explicitly requested, and must be noted as such. Records a task relies on are recorded in the task's `basis` ([§9.3](09-agent-operating-model.md#s9-3)).

**REVIEW.md (Standard §5.2.1).** Every module has a `REVIEW.md` written by its owner. The generator initializes the "What failure looks like here" section from the surface's archetype and packs, for example:

- `cap:threaded-conversation`: "an internal note reaches the customer through any channel";
- `cap:import-export`: "an exported cell is executed as a formula";
- `x:privileged-admin`: "an action runs without step-up or without an audit event".

The code owner owns this file and keeps it concise. Recurring review comments are turned into lint rules or checks (Standard §8.5). `AGENTS.md` and `REVIEW.md` at every level are control files.

## 7.5. Conformance levels (per repo and module)

The levels belong to the Standard (Standard §20.4). The table lists **the frontend criteria this profile adds** to the Standard's requirement set at each level ([§18.4](18-aisf-conformance.md#s18-4)).

| Level | Standard requirement set | Additional frontend criteria |
|---|---|---|
| **L1** Described | Standard §20.6, L1 | Valid descriptor, AGENTS.md, CODEOWNERS with backup owner, standard commands, baseline checks running (for every lifecycle) |
| **L2** Guarded | Standard §20.6, L2 | Baseline checks and Standard core checks in blocking mode; boundaries; drift check blocking; **attested evidence** (a Standard L3 item, required here from L2); merge queue; SoD check; `REVIEW.md` for each module |
| **L3** Agent-ready | Standard §20.6, L3 | Every `critical` journey in the Journey Registry ([§7.7](#s7-7)) has tests for every declared persona and scenario; stable E2E (flaky rate below threshold); the full resolved profile activated per the wave's check plan ([§8.9](08-verification.md#s8-9)), except only the groups that plan allows in `shadow`; core playbooks have run successfully; AI review at least `advisory` on critical surfaces |
| **L4** Autonomy-eligible | Standard §20.6, L4 | ≥ 1 task class at T2; rollback rehearsed; monitoring and error budget per surface; circuit breaker drilled |

**Repos and modules created by the generator reach L2 immediately**; that is precisely what the golden path means. The generator exists from Phase 1b; before that, the Slice 0 pilot repo only publishes a pilot claim (L1 plus a list of CORE-IDs, [§20.2](20-showcase.md#s20-2)), not L2. L1 only remains meaningful for code brought in from existing systems ([§16](16-current-state.md#s16)). A level only counts while a valid conformance claim exists (Standard §20.5).

## 7.6. Standard commands

| Command | Meaning | Suggested budget |
|---|---|---|
| `verify:fast` | Lint, type, unit, boundary on the affected scope | ≤ 3 minutes |
| `verify` | All static/unit/integration checks of the resolved profile | ≤ 15 minutes |
| `verify:runtime` | Boot the app with mocks + E2E/a11y/visual on affected surfaces | ≤ 30 minutes |
| `factory doctor` | Conformance, drift, coverage, registry references | ≤ 1 minute |

Exit codes: `0` pass, `1` check failure, `2` infrastructure error (→ status `ERROR`).

Standard commands are provided by the Factory CLI, at the version pinned by the policy repo. Scripts in `package.json` may alias them for convenience, but the mandatory pipeline never executes repo-defined scripts ([§8.7](08-verification.md#s8-7), Standard §7.15).

The three `verify*` commands do not decide on their own which tests to run. Each command calls the **Test Planner** ([§8.10](08-verification.md#s8-10)) with a scope, receives a test plan, then hands the plan to the runners for execution. The Planner decides the plan; runners in the mandatory pipeline execute it; evidence records both.

## 7.7. Journey Registry

A journey is the unit that criticality, E2E, coverage and the L3 criteria refer to. The registry is the platform's "feature map": fields that need judgment are declared by humans; everything else is **generated** from routes and tests.

```yaml
# journeys.yaml at the repo root — curated fields only
- id: console/compute.create-instance
  surface: console/compute
  owner: team-compute
  criticality: critical            # critical | high | normal
  personas: [owner, admin, viewer, no-access]
  permissions: [compute.instances.create]
  requirements: [req:CONSOLE-1820, req:CONSOLE-2210]   # IDs in the issue tracker; text stays in the tracker
  scenarios:                                            # versioned scenario fixtures in the generated mocks
    - { id: happy,             ac: [AC-CI-1] }
    - { id: quota-exceeded,    ac: [AC-CI-4] }
    - { id: permission-denied, ac: [AC-CI-5] }
    - { id: lro-failure,       ac: [AC-CI-6] }
  acceptance:                                           # journey-level acceptance criteria, approved by the product owner
    - { id: AC-CI-4, statement: "Insufficient quota shows the quota error and leaves no pending row" }
  evidence: [e2e, a11y, persisted-state]
```

- Playwright tests are tagged `@journey:console/compute.create-instance` and `@scenario:quota-exceeded`; scenarios come from the generated mocks.
- `factory doctor` reports: `critical` journeys missing tests for a declared persona/scenario; tests pointing to a nonexistent journey; routes in a surface with `criticality` `high` or above that belong to no journey.
- The `console-module` generator produces the journey + test + scenario skeleton; personas are generated from the IAM role catalog ([§8.8](08-verification.md#s8-8)).

**Traceability from requirement to evidence.** The registry is not just a list of journeys and E2E tests; it connects product requirements to verification results:

```text
Requirement (tracker) → Journey → Acceptance criterion (AC) → Scenario → Test case (tags) → CheckResult → VerificationRun (attested)
```

- **Requirements** stay in the issue tracker; the registry only stores IDs (`req:<KEY>`), so there are never two copies of requirement text.
- **Journey-level acceptance criteria** (`acceptance`) are durable product behavior, approved by the product owner. **A task's done checks** (`doneWhen`, [§9.3](09-agent-operating-model.md#s9-3)) are conditions of a specific change; a `doneWhen` may reference a journey AC (`ref: AC-CI-4`), or, when the task adds new behavior, propose a new AC that is added to `journeys.yaml` in the same PR.
- **Test cases** are tagged `@journey`, `@scenario` and, when checking a specific AC, `@ac`. `CheckResult.extensions["x-fe"]` records the journey, scenario and AC it covers ([§8.5](08-verification.md#s8-5)).
- `factory trace <req|journey|AC>` generates a traceability report from the Test Asset Catalog ([§8.11](08-verification.md#s8-11)) and the evidence store: which requirements have AC, which AC have tests, which tests have the most recent `PASS` evidence on which commit. `factory doctor` reports AC of `critical` journeys without tests, and tagged tests pointing to nonexistent AC.
- Editing or deleting an existing AC or scenario is an **oracle change** ([§8.6](08-verification.md#s8-6), [§9.10](09-agent-operating-model.md#s9-10)): `journeys.yaml` is a control file, and such a change requires approval by the product owner or the journey owner, never decided on its own by the implementing agent.

## 7.8. Knowledge Index: cross-product knowledge discovery and retrieval

With many repos and many products, `factory context <path>` only answers the question "which records govern this path". Agents and developers also need to search *across* repos: which ADR covers sessions, which contract has this field, which component to use for a resource table, who owns the billing service. The **Knowledge Index** solves that. It is a **retrieval layer, not a new source of truth**: every result points back to its source, and the source always wins.

**Content and generation.** The index is generated (periodically and on merge or publish), like the portfolio index:

| Node | Taken from |
|---|---|
| Knowledge Record (ADR, policy, contract spec, threat model, runbook) | Frontmatter and content in every repo |
| Contract and version | Contract registry |
| Package, component, version | Portfolio index, DS manifest ([§5.6](05-design-system.md#s5-6)) |
| SDK and version | SDK releases |
| Repo and module documentation | `AGENTS.md`, `REVIEW.md`, `README`, docs-as-code |
| Repo, surface, owner | `factory.yaml` descriptor, CODEOWNERS |

Edges between nodes use the Standard's relations (`describes`, `basedOn`, `generatedFrom`, `verifiedBy`, `implements`, `supersedes`) plus two namespaced profile relations (`x-fe:consumes`, `x-fe:owned-by`). This index is also the Standard §5.9 **dependency index** that `knowledge.impact` queries ([§7.3](#s7-3)). Each entry carries: source URI with commit SHA or revision, `status` and `authority`, `validatedAgainst`, `appliesTo` and version, owner, `visibility` and the access list inherited from the source, last verification time, and content hash.

**Retrieval rules** (apply to both humans and agents):

1. **Access follows the source.** The index never returns content the requester cannot read at the source. Permissions are filtered at query time by the requester's identity (for agents: the task's identity and scope, [§9.5](09-agent-operating-model.md#s9-5)). `restricted` content is not indexed without the owner's explicit opt-in. Being findable is not a reason to return.
2. **Default is `ACTIVE` and the correct version.** Default results include only `ACTIVE` documents whose `appliesTo` matches the versions pinned by the requester's repo. `NEEDS_REVALIDATION` documents are returned with a clear marker. Other states are only returned when explicitly requested, and are marked.
3. **Always cited.** Every result has URI@SHA, authority and version. Agents must cite the sources used in the plan and in the PR description; citations are recorded in the task log and can be re-checked.
4. **Authority still goes through `factory context`.** Search results are suggestions for orientation. The records governing a change are always determined by `factory context --diff`. When two `ACTIVE` records conflict, the agent escalates instead of choosing on its own ([§9.4](09-agent-operating-model.md#s9-4)).
5. **Retrieved content is untrusted data** ([§9.5](09-agent-operating-model.md#s9-5)): never instructions for the agent. Indexed documents also go through the same injection scanner as `review.injection-prescan`.
6. **Staleness is published.** Every answer states when the index was built; an index older than the threshold (*suggested* 24 h) is marked stale, and the agent must read directly from the source.
7. **The LLM provider data policy** ([§19.7](19-nfr-enterprise.md#s19-7), Standard §10.2) applies to embeddings and to content sent to the model: `internal` and `restricted` content is only processed by permitted providers and storage regions.

**Interface.** `factory search <query> [--kind] [--repo] [--version] [--include-draft]` and `factory context --query` ([§9.6](09-agent-operating-model.md#s9-6)), with an MCP adapter for remotely running agents. Internal search for humans shares this index.

**Technology (proposed, settled by a spike in Phase 2).** Start with lexical search plus structured filters on metadata (kind, owner, version, authority), since most agent questions are structured questions. A semantic layer (embedding/RAG) is only added when retrieval eval ([§12](12-evaluation.md#s12)) shows it improves recall without violating the rules above. Use an existing search engine; build vs buy is recorded in an ADR. Before building, an existing developer portal or catalog (e.g., Backstage) is evaluated as the host for the index ([§17](17-decisions-to-make.md#s17)); the retrieval rules above apply whichever option is chosen.
